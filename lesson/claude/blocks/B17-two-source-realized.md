# B17 · 雙來源已實現對帳

## 它解決什麼

券商給了一份已實現損益表。成交簿也能算已實現損益。**兩個數字不一樣。**

預設反應是「哪個對？」然後選一個。**這是錯的問題。**

## 兩者算的是不同的東西

| | 券商 | 成交簿 |
|---|---|---|
| 成本基礎 | 券商自己的，會因公司行動調整 | 買進當下實付現金 |
| 配息 | 調降成本 → 出現在已實現裡 | 不影響（配息現金另計） |
| 減資／股票股利 | 調整成本與股數 | 需要另外記錄 |

**兩個都不算錯。** 它們回答的是不同的問題：

- 券商：「這筆投資到目前為止總共替我賺了多少」（含配息）
- 成交簿：「這筆交易本身的現金流結果是多少」（純交易）

## 契約

```python
broker_realized_reconciliation(fills) -> {
    "rows",          # 逐筆：券商 / 成交簿 / 差額 / 每股差 / 歸因
    "broker_total", "book_total", "gap",
}
```

配對鍵是 `(賣出日, 股票代碼, 賣出價)` —— **不是委託單號**，因為兩份文件的單號欄位未必一致，而這三個欄位是共同的自然鍵。

## 關鍵：把差額除以股數

```python
per_share = gap / shares
```

這一步把一個說不清的總差額，變成一個**可辨識的簽名**：

```python
if abs(abs(per_share) - 1.0) < 0.02:
    note = "每股 ±1.0000，配息調整成本"
```

在一個真實案例裡，某檔的差額除以股數剛好是 **1.0000**，橫跨兩次不同日期、不同股數的出場。**那不可能是巧合** —— 那是每股 1 元的配息。

## 真實產出的形狀（去識別）

| 賣出日 | 券商 | 成交簿 | 差額 | 每股 | 歸因 |
|---|---:|---:|---:|---:|---|
| D1 | +A | +A | 0 | — | 一致 |
| D2 | +B | +B−3000 | +3,000 | **+1.0000** | 配息 |
| D3 | +C | +C−949 | +949 | **+1.0000** | 同一檔，同樣配息 |
| D4 | +D | +D−708 | +708 | +1.37 | 成本基礎差異 |
| 其餘 | | | **0** | — | 完全一致 |

**十二筆裡有七筆完全一致，剩下五筆的差額全部落在先前已經標示過成本異動的個股上。**

這就是這個積木的價值：它不只說「差了多少」，它說**「差在哪一檔、每股差多少、為什麼」**，而且結論指向一個**具體缺少的紀錄** —— 那筆配息現金從來沒有被寫進成交簿。

## 為什麼並排比選一邊誠實

選一邊會發生兩件事：

1. 另一邊的資訊消失。選了券商，你就看不到「純交易的結果」；選了成交簿，你就漏掉配息收益。
2. **差額變成不存在。** 而差額正是唯一告訴你「有東西沒記到」的訊號。

並排 + 逐筆歸因，把「兩個數字打架」變成「這裡少一列」。

## 陷阱

**陷阱 1：用委託單號配對。**
券商的已實現表和成交回報表可能用不同的單號欄位，或把多張單合併成一列。用 `(日期, 代碼, 價格)` 這種自然鍵。

**陷阱 2：同一天同一檔不同價格的多筆出場。**
配對鍵一定要含價格，否則兩筆會被合成一筆，差額歸因就亂了。

**陷阱 3：把差額直接調進成交簿讓它「對上」。**
這會消滅證據。正確做法是**補上真正缺少的那一列**（配息收入），讓它自然收斂。

**陷阱 4：以為差額為零就沒事。**
差額為零只代表這兩個來源一致，不代表都對。兩份文件可能來自同一個上游錯誤。

## 一般化

任何時候你有**兩個獨立來源在算同一件事**，正確的做法都是：

1. 逐筆配對，用自然鍵
2. 算差額，並**除以一個有意義的分母**（股數、天數、筆數）看有沒有簽名
3. 把差額歸因到具體的列，不是掛在總額上
4. 結論寫成「缺什麼」，不是「誰對」

> 差額不是要消滅的誤差，是資料在告訴你哪裡有一個你還不知道的事件。
